Fraud Decision Engine

An API that answers one question per purchase in a few milliseconds: approve it, ask for an extra check, or decline it. This page walks through what it does, how the model was evaluated, what a better model was actually worth, and what is watched once it is live.

Every number here comes from the project's own evaluation files on the public Fraud_Data set (151,112 purchases, one per user). Test period: the last 20% by time, never used for training.

What happens to one request

Rules first, then a model, then a cost-based decision

A purchase is posted to /api/transactions. Cheap, certain checks run first and can end the request before the model is called. Whatever happens, the decision is written to an audit table with the features, the score and the rule that decided.

  • Score compared with two thresholds picked by cost

Audit, then update

  • One row per decision: features, score, rule, model version

What did not help

Signup hour and weekday, raw age, seconds from signup to purchase, whether the device or IP appeared in the January bot attack, and delayed fraud labels per device. All within ±0.002 of the baseline.

What the better model is worth

Better ranking was worth $0 until there was a third decision

The fraud the new feature finds sits at about 23% precision. A decline at that precision barely pays for the good customers it turns away, so behind allow or deny the better model caught four times the fraud for the same total cost. The engine got a middle outcome, review, and picks both thresholds by cost. Move the assumptions and the policy is re-picked on validation data and scored on the test period, exactly as the training script does it.

Total cost = fraud dollars that get through + declines of good customers + every review. Thresholds: the cheapest pair on validation, then the gentlest policy within 1% of it. The review cost and catch rate are assumptions, which is why they are sliders.

Once it is live

What is watched, what alerts, and what is not covered yet

A local replay, 200 requests per second

Latency: p50 7 ms · p95 11 ms · p99 15 ms on one laptop, eight workers. Average worker CPU 10%, event-loop lag 4 ms.

On the Grafana dashboard

  • Decision mix: allow, review, deny over time
  • Decisions by rule, and shadow-rule hits
  • Score distribution against the two served thresholds
  • Share of traffic from devices other accounts have used
  • Latency per step: features, model, database write

Four golden signals

  • Latency: p50, p99 and per step
  • Traffic: rate against its 1-day average, requests in flight
  • Errors: our failures, invalid requests, duplicates in flight
  • Saturation: worker CPU, event-loop lag, database pool and connections, Redis memory

Action rates, not accuracy

Live traffic has no labels, so nobody can say whether a live decision was right. What is watched instead is what the engine tells callers to do: the share of allow, review and deny against the last day and against what training expected, and the share per rule. Accuracy is measured offline, on labelled history, at every retrain.

Drift

The score and eight inputs are compared with buckets saved at training time (PSI). On unseen months the score sits at 0.004 or less, far below the 0.10 alert level. Its first day found three flawed inputs, one of them in a model shipped hours earlier.

29 alerts, each with a runbook

  • Every alert has a severity, a minimum-traffic guard and a "check first" section
  • 19 rule scenarios run in CI with promtool
  • A drill sends a bot burst and watches the alert reach Alertmanager
  • No notification channel in the repository: a webhook is a secret
Things that went wrong, and what they taught

Findings worth an interview question

The offline numbers were right and the feature was wrong

The first version counted every earlier purchase on the device. On this dataset each user buys once, so that equals "other accounts". Sent through the live system, a loyal customer's second purchase went to review. Found by a hand-made request the day it shipped; fixed by making the feature mean what the model had learned.

Early stopping that stopped at tree 1

XGBoost's and CatBoost's built-in PR-AUC over-credit a one-tree model (0.088 where scikit-learn says 0.077). One fold kept a single tree, which made two other algorithms look significantly better. Tree counts are now picked with scikit-learn's metric.

A model that trained but could not be served

A constraint saved in one form trained and scored fine, then failed the moment the API adjusted a setting on the loaded model. No test used the real model file. Shipping now reloads the saved file the way the API does and compares scores first, and four tests run against the real file.

A ship gate that passed a worthless model

The gate compared ranking quality only. A model passed it while saving no money. The gate now also requires the new policy to cost no more than the served one, with an interval on the difference.

Training and serving compute the same thing

Counters use the purchase's own time, not the server clock, so a replay of history fills windows exactly as training did. A test replays 5,000 real rows through the API code and compares every feature.

January was a bot attack, not a pattern

7,600 purchases within a second of signup, all fraud, all in one month. A model trained on them learns "January means fraud". They are handled by a rule and removed from training.

Nine inputs removed, nothing lost

The dataset has no repeat customers, so a feature can be right on it and wrong on real traffic. After three were caught by three different methods, every input was audited with one question: does it mean the same thing when a customer comes back? Nine did not. Sex and age, measured to add nothing, were removed too. Accuracy is unchanged and the score distribution now holds still on unseen months.

Limits stated up front

Public, simulated-looking data. Scores are not probabilities. Review cost and catch rate are assumed. Live decision accuracy is not measured. Alert thresholds are reasoned starting points, not tuned on production traffic.
